# 技術選擇大抉擇決策指南 (Technology Decision Guide)

**協助你在如同繁星般的不同資料庫、快取軍團、雲端霸主軍閥等諸多技術堆疊選項中，做出明智無悔的抉擇。**

## 1. 資料庫之戰 (Database Selection)

| 技術門派名稱 (Type) | 何時該祭出神兵 (When to Use) | 何時該閃避退縮 (When NOT to Use) | 江湖代表人物 (Examples) |
|------|-------------|-----------------|----------|
| 關聯型王道 (SQL) | 當你對於「一致性交易 (ACID)」絕不妥協時、有超複雜要東黏西接 (JOIN) 的資料、當你現在還搞不清楚要不要亂長欄位時。 | 拿這個去存沒有特定長相的文字黑歷史或是無限長度的機器 log 日誌時、需要瘋狂「平行分開 (Horizontal)」成長的終極超大地圖。 | PostgreSQL, MySQL, SQL Server, Oracle |
| 文件歸檔總倉 (Document / NoSQL) | 新創剛起步對未來 schema 長怎樣沒個譜、想要把相關的東西全塞一個箱子裡查出來、需要狂野且便宜的平行分散與成長時。 | 想把兩三個不同國家的檔案連結強硬串接在一起 (JOIN)、如果你每一筆交易都要綁連坐責任時。 | MongoDB, DynamoDB, CouchDB |
| 字典型神速暗櫃 (Key-Value) | 需要這輩子見過最狂野的神速讀取且幾乎不會失誤時、使用當成快取、那些活不過幾個小時的時效票券 Session 或者限流計算器時。 | 你試圖想要在那幾百萬把鑰匙 (Key) 當中搜索出長著某個特定值 (Value) 的保險箱時 (超複雜查詢)。 | Redis, Memcached, Riak |
| 全欄位式通查巨無霸 (Column-Family) | 每天要吞噬數萬 TB 計的大數據怪獸時段、以歷史順序堆疊且極少需要再修改回去的神奇長條時間日曆 (Time-series)、做成報表儀表板時。 | 如果你真的很容易後悔想要常常改以前寫入的舊資料時、對付那種錯綜複雜的相互關聯網時。 | Cassandra, HBase, ScyllaDB |
| 龐大關係蜘蛛網 (Graph) | 分析好幾萬個好友名單內的好友之間彼此認識不認識的關係鏈時 (推薦演算法)、拿來抓可疑洗錢異常名單網路時。 | 只是一張寫下誰欠誰錢的呆板兩欄表 (Flat, disconnected data)。 | Neo4j, Amazon Neptune, ArangoDB |
| 強力搜尋雷達系統 (Search Engine) | 全文檢索搜索字詞、打錯字自動腦補尋找 (Fuzzy matching)、想要從無邊無際的文字海裡做過濾撈金時。 | 真的把它拿來當你整個村子的唯一保命用命脈主資料庫。 | Elasticsearch, Solr, Meilisearch |

### 「我要用那套資料嗎」的快速隨堂考決策樹 (Database Decision Tree):
1. **你的資料有著極度錯綜複雜又長長一串的深交連結關係嗎?** -> Graph DB (圖形相連資料庫)
2. **請問你是否有一堆連你阿公阿嬤都猜不到長什麼樣的不固定欄位資料，但你又要很快把它們全拉出來?** -> Document DB (隨心所欲加減欄位的文件資料庫)
3. **這玩意需要你這輩子遇過最殘暴且連零點幾秒也不能等的毫秒級讀取神速嗎?** -> Key-Value DB (快取記憶體為主的字典型資料庫)
4. **你需要那種強迫症發作似的嚴謹保證金流交易成功 (ACID)?** -> SQL DB (關聯型老司機)
5. **你的資料就像流水瀑布一樣永無止盡的掉進來且不用管嚴謹對應結構嗎?** -> Column-Family DB (寫不完的欄位家族)

## 2. 暫存快取兵法論 (Caching Strategy)

| 各派戰略名稱 (Strategy) | 它的神聖之處 (How it Works) | 讚賞歌頌 (Pros) | 唾棄缺點 (Cons) | 什麼場合最好用 (When to Use) |
|----------|-------------|------|------|-------------|
| 隨手即塞快遞法 (Cache-Aside) | 程式本人先去查快取沒有就跑去金庫資料庫搬，搬完順手放一把到快取區裡。 | 如果快遞小哥死在半野外當機了，系統勉強還能動只是比較慢而已 (因為會直上總資料庫要)。資料模式也是想變就變。 | 程式碼會稍微醜一點，然後第一次那件資料鐵定沒人查過會卡很久 (Cache miss penalty)。 | 那些常常有人愛看但沒幾個人會去改的萬年布告欄 (讀多寫少 Read-heavy)。 |
| 一條龍暗管塞法 (Read-Through) | 程式只要對著快遞員要貨，如果沒貨，快遞員自己會去資料庫總倉挖寶再給你。 | 開發者省下很多寫判斷的垃圾程式碼，因為快遞會全套幫你做到好。 | 剛出來時第一次去要貨還是要等滿久的，而且系統被綁死特定那套框架裡。 | 當你的讀取極其瘋狂且背後框架支援這種神技時。 |
| 同步寫入雙生流 (Write-Through)| 程式對著快取寫入，然後這套快取會「等待」底層總倉資料庫也安穩寫好後，這筆才算完工。 | 你這輩子讀出來的快遞貨保證都是最新鮮沒過期的正確好貨。 | 要寫進去時等同經過兩道關卡，會把「寫入」動作拖慢到極點。 | 如果這東西你隨時需要更新又要保證萬無一失沒時差時。 |
| 射後不理堆疊法 (Write-Behind) | 程式把資料丟給快遞就當寫完直接說掰掰，這快遞累積一坨後再自己慢慢分批丟回底層總家資料庫裡。 | 「寫」東西進去的速度神快！然後對底城總資料庫也不會有沉重撞擊。 | 如果大塞車時那台快遞機不小心燒毀當機了，你最後那批可能就灰飛煙滅找不回來。 | 面對瘋狂海量倒進來的每秒寫入操作 (Write-heavy)。 |

## 3. 非同步投遞與訊息總路線管家 (Messaging and Queues)

| 派系流別 (Tech) | 什麼時候該放出來咬人 (When to Use) | 最經典代表作 (Examples) | 背後藏著的特性與精神 |
|------|-------------|----------|----------------|
| 點對點任務交辦單 (Message Queues)| 丟過去一筆工作只會有「一個人」去認領把它做掉，當下想把這個極度廢時的事情留著晚點做時使用 (任務派發、工作轉交)。 | RabbitMQ, SQS, ActiveMQ | 做完就丟掉 (丟入無盡虛空)、可以像切西瓜一樣在數萬兵馬中平均分散苦役。 |
| 大聲公全村廣播系統 (Pub/Sub) | 拿著大聲公廣播「有新事發生了!」，底下有訂閱的無數個系統全村都會一起衝過來要資料做動作 (廣播體操式操作)。 | SNS, Google Cloud Pub/Sub | 誰有訂報紙就全發給他一份報紙看，送到了就隨風散去不留存根。 |
| 史詩級連載日誌之壁 (Event Streaming)| 像播放影帶一樣，永遠紀錄下世界發生的一切並留給後人去「倒帶」重看了又看；或是面對萬獸奔騰的海量狂暴訊息流。 | Kafka, Kinesis, Pulsar | 東西發出去了這輩子不輕易灰飛煙滅、可以保證誰先發誰後到不亂掉、就算有百萬支大軍也能承載得起。 |

## 4. 這到底是誰在敲門認證術 (Authentication Methods)

| 查驗流別 (Method) | 在講什麼東西 (What it is) | 讚賞歌頌 (Pros) | 唾棄缺點 (Cons) | 什麼場合最好用 (When to Use) |
|--------|------------|------|------|-------------|
| 對獎存根聯法 (Session-based) | 伺服器會把你這流浪漢的特徵寫在一張便利貼死死貼在身上並記下流水編號，給你一串暗號存著。 | 開發連腳本小鬼都會、你想瞬間當面把那個流浪漢踢掉取消資格超級簡單。 | 一旦你要把伺服器從一台變成一萬台，這堆便利貼到底要貼在哪台機器就是一場悲劇 (需要靠 Redis 來集中貼)。 | 古典標準不用太複雜的單純網站應用 (Web apps)。 |
| 神奇魔法長文憑 (JWT/Token) | 你就是拿著一份發給你就改不了的魔法證書 (自己裡面已經寫滿了這張是身分、權限到期日)，伺服器只要看它沒仿冒被變造過就會放你過。 | 完全無狀態免操心伺服器，你今天換到幾千台分所一樣都承認這個魔法證書而且行動自如。 | 你發出去後直到他「時效到」為止，你這張文憑基本上就是無法註銷撤回 (Revocation is hard)、且那串咒語會很長很佔頻寬空間。 | 單純前後端切得亂七八糟互相不認識的世界 (Single Page Apps、無數支互相呼叫的 API)、不用去中心化伺服器的分散天下 (Microservices)。 |
| 他人授權護身符 (OAuth 2.0) | 請某位更有影響力的大老闆 (如 Google、Facebook) 單純發給你一張只可以拿來看某本古書的有限時限證件來做代理使用。 | 你不需要自己當壞人去強暴人家要密碼儲藏、權限可以被切的碎碎好切割授權。 | 這鬼規矩光是要能走完且實作出來會耗費工程師半條命。 | 可以讓別人點「用我的 XXX 帳號快登」、你寫的軟體只是要請人家拿資料去打第三方 API 時使用。 |

## 5. 無腦上雲大比拼 (Cloud Provider Selection)

| 當紅炸子雞 (Provider) | 該廠商引以為傲的最強絕招 (Strengths) | 當選這套的人到底在想啥 (Best for) | 值得你去當個酸民的事蹟 (Considerations) |
|----------|------------|----------|----------------|
| 亞馬遜之神 AWS | 東西多到你根本看都看不懂、世界上最恐怖且巨大生態圈之神、在任何國家都幾乎不會斷。 | 就是想要超大規模橫跨各大陸的人、需要無窮盡服務任君點擊，以及所有企業級霸主要求的一切。 | 一堆連工程師可能都會看錯甚至設定成地獄的門檻與鬼名詞組合。 |
| 谷歌地球 Google Cloud (GCP) | 機器學習與數學大神，算你這輩子遇過最暴力的巨無霸數據群時、想要爽用天下第一的 Kubernetes 大本營。 | 與大數據資料作戰的團隊、極致微服務信徒、愛死開源軟體不離不棄者。 | 不賺錢的老闆有極短線思維，隨時會把不賺錢的服務大禮包直接砍了放生你。 |
| 微軟老爺爺 Microsoft Azure | 不容許任何失誤的企業死守信徒、跟他們家賣的那堆 Windows, Office 根本就是親兄弟完美結合。 | 公司本身就是靠寫 C# 跟用死板舊微軟科技維生的財團、或是擁有終極高額老企業合約的超級大戶。 | 不好上手也不一定適合開給非微軟系的單打獨鬥孤狼駭客使用。 |

## 6. API 流派宗教大戰 (API Style Guide)

| 大宗流派 (Style) | 本質運作邏輯 (Model) | 讚賞歌頌 (Pros) | 唾棄缺點 (Cons) | 江湖老點 (Best for) |
|-------|-------|------|------|----------|
| 經典名流 REST | 就只是在針對名詞「物件」打打殺殺。 | 大家從幼稚園就會寫、各種工具或瀏覽器直接拿著看都行、要快取更是好抓。 | 常常一次會吐回連你家祖宗十八代你根本不想看的多餘資料包 (Over-fetching)、或是得為了組合這張畫面打十支 API (Under-fetching)。 | 幾乎橫掃世界上一切沒有意外都該選這個的基本款公開介面 (Public web APIs)。 |
| 圖譜之網 GraphQL| 拿著空白清單上去跟後端對點「我就只想要這些」，後端會東拼西湊端出一盤你剛好點的套餐給您。 | 客戶端超強勢想拿什麼就打什麼絕不多浪費頻寬位元組、一次把千絲萬縷全在一根 Request 把他撈回。 | 後端自己本身如果對應不到可能會累死成一團泥、還有你別想太指望瀏覽器天生的超快快取能夠保住你。 | 前端手機 App 超重視網路耗能時、錯綜複雜跟蜘蛛網一樣的交纏資料、或是常常要修修改改畫面長相的前置端點。 |
| 強硬遙控器 gRPC | 強硬執行「我就要對你下這個遙控指令」。 | 嚴明立下神聖契約與規矩、編出的檔案超級無敵迷你爆快、天生支援這通那不中斷的 Streams。 | 前端的 JavaScript 根本看不懂這鬼東西很難直接接(需要另架轉接頭)、對工程師單純想打開看是啥根本像看天書 (Not human-readable)。 | 深山裡頭兩隻互相都不見天日的後端純種微服務間 (Microservices)、或是重視超低延遲跟體積超窄的行動裝置連網路線。 |
