# API 文件撰寫

撰寫 API 文件 SOP / Checklist
不一定要產出實體檔案，可直接在回應中提供內容；只有使用者要求時才建立文件。

## 0. 前置確認（開始前）

- 已確認 API 名稱
- 已確認 API 是否已存在（新建 / 修改）
- 已確認主要呼叫端（Frontend / Service / 外部系統）

**完成標準**：

> 我知道這支 API 是「誰在用、用在哪」。

---

## 1. Method / Route

- 已填寫 HTTP Method（GET / POST / PUT / DELETE）
- 已填寫完整 Route（含 version）
- Route 命名符合 REST / 團隊規範
- 無重複或語意不清的路徑

**完成標準**：

> 一看就知道這支 API 在「做什麼動作」。

---

## 2. API 功能（What）

- 已用一句話說明 API 功能
- 已說明主要用途
- 未描述實作細節
- 非 Backend 也能理解

**完成標準**：

> 不看程式碼也知道這支 API 能幹嘛。

---

## 3. 業務邏輯（How）

- 已用步驟描述邏輯流程
- 已說明關鍵判斷條件
- 已描述成功與失敗流程
- 未出現程式碼或 SQL

**完成標準**：

> Reviewer 能快速理解整體邏輯。

---

## 4. 使用權限（Who）

- 已標註是否需登入
- 已標註角色 / 權限限制
- 已說明 token / header 需求
- 已說明權限不足的回傳結果

**完成標準**：

> 不會出現「怎麼誰都打得到」的風險。

---

## 5. 傳入參數說明（Input）

- 已列出所有必要與非必要參數
- 已說明參數代表含意
- 已標註格式與型別
- 已標註是否必填
- 已說明限制條件（長度 / 範圍）

**完成標準**：

> Frontend 不用猜參數怎麼傳。

### 參數表（範例）

| 參數   | 代表含意  | 格式   | 說明              |
| ------ | --------- | ------ | ----------------- |
| userId | 使用者 ID | number | 必填              |
| status | 狀態      | string | 選填，預設 ACTIVE |

---

## 6. 回傳訊息（Response）

- 已定義所有 rtnCode / rtnMsg
- 已區分成功與失敗情境
- rtnCode 有一致命名規則
- 已說明錯誤發生條件

**完成標準**：

> 呼叫端知道怎麼判斷結果。

### 回傳碼表（範例）

| `rtnCode` | `rtnMsg`          |
| --------- | ----------------- |
| 0000      | Success           |
| 1001      | Invalid parameter |
| 2001      | Permission denied |

---

### 成功範例

- 已提供完整成功 response
- 格式與實際回傳一致
- 欄位意義清楚

```json
{
  "rtnCode": "0000",
  "rtnMsg": "Success",
  "data": {
    "result": true
  }
}
```

---

## 7. 對資料表欄位的影響（Data Impact）

- 已列出所有存取的資料表
- 已標註欄位操作行為
- 已說明每個異動目的
- 已確認是否有 DELETE 或不可逆異動

**完成標準**：

> DB 影響一目了然。

| 資料表 | 欄位   | 動作   | 說明           |
| ------ | ------ | ------ | -------------- |
| user   | status | UPDATE | 更新使用者狀態 |
| log    | \*     | INSERT | 紀錄操作行為   |

---

## 8. 資料流（Data Flow）

- 已描述資料來源
- 已描述 API 內部處理
- 已描述資料輸出
- 已標註是否跨系統

**完成標準**：

> 架構與資料流向清楚。

---

## 9. 注意事項（Notes）

- 已標註是否具 idempotent 特性
- 已說明效能或流量限制
- 已說明例外情境
- 已標註版本相容性
- 已說明是否需同步修改其他 API

**完成標準**：

> 未來修改不會踩雷。
