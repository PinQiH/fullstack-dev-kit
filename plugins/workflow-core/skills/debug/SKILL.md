# 系統化除錯

依下列流程找出根本原因。修改程式碼前，先回報原因與修復方案。

## 除錯流程

請遵循以下系統化的除錯方法：

### 1. **理解問題**
- 預期的行為是什麼？
- 實際發生的行為是什麼？
- 你能穩定重現這個問題嗎？
- 這個問題是從什麼時候開始發生的？
- 最近有什麼變更？

### 2. **收集資訊**
- 錯誤訊息與堆疊追蹤
- Log 檔案與錯誤日誌
- 環境細節 (作業系統、版本、設定檔)
- 觸發此問題的輸入資料
- 發生前/中/後的系統狀態

### 3. **形成假設**
- 最可能的原因是什麼？
- 將假設依照可能性從高到底列出
- 考量面向：邏輯錯誤、資料異常、環境問題、時間點/非同步干擾、依賴套件

### 4. **驗證假設**
- 使用二分搜尋法來縮小範圍
- 在關鍵位置加入 log/print 語句
- 使用 debugger 的中斷點
- 隔離各個組件來測試
- 使用最小的可重現案例進行測試

### 5. **找出根本原因**
- 不要只停留在治療表面症狀 —— 找出真正的起因
- 用證據來驗證你的發現
- 了解為什麼這問題沒有在更早的階段被發現

### 6. **回報並等待確認**
- 先向使用者回報：根本原因、證據、建議的修復方案與影響範圍
- 有多個修法時列出取捨，並給出建議
- 等使用者確認後才修改程式碼；使用者已明確要求「直接修」時可略過等待，但仍要先回報原因

### 7. **修復與驗證**
- 實作使用者確認的修復方案
- 徹底測試這個修復
- 確保沒有引入新的退化問題
- 新增測試案例以防止未來再次發生

## 除錯策略

### 二分搜尋法
```
1. 辨識程式碼區間 (起點 → 終點)
2. 檢查中間點
3. 如果 bug 存在 → 搜尋左半邊
4. 如果 bug 不在 → 搜尋右半邊
5. 重複直到隔離出問題點
```

### 黃色小鴨除錯法
- 逐行解釋程式碼
- 經常能在口述/具象化表達的過程中發現問題
- 能夠釐清盲點與預設的假設

### 策略性地加入 Log (Add Strategic Logging)
```python
# 在進入 function 時
print(f"[DEBUG] function_name 傳入了: {args}")

# 在決策分支點
print(f"[DEBUG] 條件 X 的結果為 {condition_result}")

# 在變更狀態的前/後
print(f"[DEBUG] 變更前: {state}, 變更後: {new_state}")
```

### 二分法尋找退化版本
```bash
# 找出是哪個 commit 引入了這個 bug
git bisect start
git bisect bad HEAD
git bisect good <last-known-good-commit>
# 測試每一個版本直到找出真兇
```

## 常見的 Bug 模式

### 差一錯誤
- 迴圈的索引 (`i < n` vs `i <= n`)
- 陣列邊界 (`arr[len(arr)]` 而不是 `arr[len(arr)-1]`)

### Null/Undefined 參考
- 在使用變數前未進行檢查
- 沒確認 API 的回應是否有包含預期的欄位

### 競爭危害
- 非同步操作以非預期的順序完成
- 共用的狀態沒有上鎖操作

### 型別不符
- 字串與數字之間的比較
- 隱性轉型的問題

### 過期的狀態
- 快取的值沒有被更新
- 閉包捕捉到了舊的變數

## 輸出格式

請依照以下結構呈現你的除錯分析報告：

```markdown
## 問題描述
[清晰地描述此問題]

## 環境資訊
- [相關的版本/組態設定資訊]

## 錯誤分析
[對錯誤訊息/堆疊追蹤進行分析]

## 假設清單 *依優先權排序*
1. **[最有可能]**: [推論原因]
2. **[次有可能]**: [推論原因]
3. **[較不可能]**: [推論原因]

## 調查步驟
1. [第一步要檢查什麼]
2. [如何驗證假設]
3. [從結果做出的下一步行動]

## 根本原因
[一旦找出來後，解釋其背後的問題機制]

## 修復方案
[建議修改的位置與做法；確認前不修改程式碼]

## 預防措施
[未來該如何避免這個問題再次發生]
```
