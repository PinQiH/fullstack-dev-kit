# 技術文件寫作風格

目標：讀者看一次就懂，且不會有第二種讀法。
規則來自 ASD-STE100 的精神（短句、一詞一義、主動語態、一步一動作），改寫成適用繁體中文的版本。這不是官方 STE 標準。

## 適用範圍

- 適用：README、SOP、操作手冊、runbook、設計文件、規格、交接文件、API 與元件說明。
- 不適用：對話回覆、程式註解（見 `comment-conventions`）、commit message（見 `git-commit`）。
- 使用者明確指定其他風格時，以使用者為準。

## 句子

- 一句只講一件事。超過 35 字就檢查能否拆開。
- 用主動語態，寫出誰做什麼：「系統寫入 log」，不寫「log 被寫入」。
- 動詞直接用，不加「進行」「予以」「加以」：「驗證 token」，不寫「進行 token 的驗證」。
- 能用肯定句就不用否定句：「只接受 UTF-8」，不寫「不接受非 UTF-8」。
- 刪除填充語：「值得注意的是」「基本上」「總而言之」「如前所述」。

## 步驟

- 一步一個動作，用祈使句，依序編號。
- 條件放在動作前面：「若 token 過期，重新登入」。
- 警告放在它所保護的步驟之前，不放在之後。
- 每個步驟寫明預期結果或驗證方式。

## 用詞

- 一詞一義：同一個概念全文只用一個詞，不為了避免重複而換同義詞（不要「使用者」「用戶」「會員」混用）。
- 首次出現的專有名詞先定義，之後固定使用。
- 禁止模糊詞：「適當」「相關」「必要時」「盡量」「視情況」。改寫成具體條件、數值或對象。
- 強度用固定詞：必須（不做會出錯）、禁止、建議（可不做但有風險）、可以（選項）。
- 數字用阿拉伯數字並帶單位：「30 秒」「3 次」。
- 指令、路徑、檔名、欄位名、版本號用 code 格式。
- 使用台灣慣用詞與全形標點；英文術語與識別字保持原樣。

## 結構

- 結論先行：第一段說明這份文件解決什麼問題與結果。
- 一段一主題，不超過 5 句。
- 並列 3 項以上改用列表；比較多個屬性改用表格。
- 標題寫內容，不寫口號：「重設密碼的步驟」，不寫「讓我們開始吧」。

## 範例

改寫前：
> 在進行部署之前，值得注意的是，必要時應該要適當地備份相關的資料，否則可能會導致資料遺失的情況發生。

改寫後：
> 警告：部署會覆寫 `data/` 目錄。
> 1. 執行 `npm run backup`，產生 `backup/data-<日期>.zip`。
> 2. 確認 zip 檔大小大於 0 KB。
> 3. 執行 `npm run deploy`。

## 交稿前自我檢查

- 有沒有超過 35 字且含兩個以上動作的句子？
- 同一概念是否出現兩種以上說法？
- 有沒有「適當」「相關」「必要時」這類無法驗證的詞？
- 步驟是否一步一動作，且警告在步驟之前？
- 去 AI 味、校正用語屬於另一件事，需要時使用 `speak-human-tw`（若已安裝）。
